SHEET 03 / 06 — DWG. F000‑SCMP‑C

Scaffold Mutations

Seven stock operations applied directly to the scaffold's own structure. Technique: SCAMPER Method.
Technique 03
S
Substitute
  • Hand‑written DTO/JSON mapping → freezed + json_serializable for Entry, ChatMessage, ExportJob
  • Per‑feature loading‑error‑data state classes → one generic Resource sealed class shared from core
  • Hand‑rolled debounce Timer in RF06 → one reusable Debouncer utility in core
C
Combine
  • HTTP client + offline‑cache read path behind one repository‑facing helper — features never choose network vs. cache
  • design_tokens.dart generation + a golden‑screenshot test step — RNF08 fidelity partly machine‑checked
  • Auth vault + session‑refresh logic → one AppStartupGate owning both
  • Vault background timeout + HTTP token‑refresh timing driven from one shared app‑lifecycle clock, not two drifting timers
A
Adapt
  • The closed 13‑code backend error taxonomy → a generated Dart enum, exhaustiveness‑checkable
  • Every screen's multiple visible states (RF02's four, RF04's three) → instances of one generic view‑state enum
M
Magnify / Shrink
  • Magnify — invest more than F000 strictly needs in the fake‑clock / fake‑HTTP test harness; the RNF07 target multiplies across nine more units
  • Shrink — scope F000 navigation to exactly the skeleton the flowchart needs: splash → vault → home → side menu, nothing speculative beyond it
P
Put to other use
  • The design‑token generator also emits a ThemeData object, not just raw constants — widgets read Theme.of(context) with less import noise
  • Reuse the dio retry interceptor's backoff policy for RF05 export‑job status polling instead of a separate poller
E
Eliminate
  • No home‑grown JWT parsing — hold Supabase tokens opaque; auth/refresh and auth/session are the only source of validity
  • No speculative future‑platform abstractions — iOS‑portrait‑only already forbids needing them
  • No shared god repository interface — each feature repository stays in its own domain layer per RNF06
  • No generic BaseRepository with shared CRUD — independent repositories, no base that could tempt cross‑imports
R
Reverse
  • Write the Failure hierarchy and the 15‑scenario RNF09 harness before the first real HTTP call is wired — every repository built test‑first
  • Let the router itself redirect on a single AuthStatus stream — screens stay dumb instead of each checking auth state on build
  • Shape RF10's shared save‑use‑case interface in F000, before RF04 or RF01 exist — RNF06 satisfied by construction, not retrofit
SHEET 04 / 06 — DWG. F000‑FP‑D

Bedrock Facts & Superstructure

Shared patterns rebuilt from bedrock facts, not from habit. Technique: First Principles Thinking.
Technique 04

Everything above the grade line below is derived — it stands only because of the irreducible facts stacked underneath it.

Failure hierarchy mirrors the 13 backend codes + exactly one local‑only variant
One SessionStatus stream — valid / expired — every bloc subscribes, nothing decides independently
Vault rebuilt synchronous, no Either plumbing — it is 100% local
One isolatedSideEffect helper shared by RF08 and RF10
— grade line —
Every repository returns Either<Failure, T> — the Failure shape should mirror the backend error shape plus exactly one local‑only variant.
Retryable is a server‑asserted flag — the try‑again button renders purely on retryable being true, never on client‑side guessing.
Session state is binary, valid or expired — exactly one SessionStatus stream, nothing else independently decides login state.
The vault is 100% local — threading a synchronous local decision through the same Either as network calls would be over‑engineering.
Entries are immutable, no PATCH or DELETE — the entries repository interface should never expose update or delete, not even as stubs.
Offline allows only viewing cached data, never writing — createEntry and sendMessage have no offline code path, no optimistic queueing.
RF08 and RF10 explicitly share the same failure‑isolation pattern — permission to build one isolatedSideEffect helper, not two parallel implementations.
PII check and embedding happen inside POST /entries — the client needs zero PII‑awareness logic, resist client‑side pre‑filtering.
The spec explicitly states no risk‑signal detection as a scope decision — don't add defensive risk‑detection hooks "just in case." That door is deliberately closed.
design_tokens.dart is the single source with zero hardcoded values allowed — no screen widget holds even one temporary literal color or number.
"No BLoC imports another BLoC" is stated for RF07 but is really whole‑app — cross‑feature communication stays repository/stream level everywhere.
Chat messages never become entries automatically except the explicit RF10 action — chat and entries are genuinely separate aggregates, resisting a shared Record supertype.
The background session timeout is fixed and explicitly not configurable — a hardcoded Duration constant in core, never exposed through Settings.
whisper_ggml never sends audio to the backend — the RF02 domain use case takes raw audio in, text out, with zero awareness of where transcription runs.
The 13 backend error codes are a closed set — the Failure‑mapping function switches with no default case; a hypothetical 14th code becomes a compile error.
★InsightSecure storage and biometrics are really one decision, the vault, not two independent parameters — worth collapsing in any eventual decision matrix.
★InsightThe shared failure‑isolation wording for RF08 and RF10 reads as a spec‑level hint toward one shared helper, not a coincidence of similar phrasing.
★InsightF000's real deliverable isn't picking seven libraries — it's building the two or three shared abstractions that make every later RF unit boring to implement.
Open — Q95 — Should F000 also decide the test‑fixture strategy for shaping fake HTTP responses, given RNF09 needs 15 scenarios across only 5 write endpoints — or should that be deferred to each RF unit?
