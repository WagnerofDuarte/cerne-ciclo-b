# Review — Backend-doc fidelity of ARCHITECTURE-SPINE.md

**Verdict: minor gaps.** AD-3, AD-4, AD-5, and AD-11 are faithful, exact restatements of `error-taxonomy.md`, `README.md`'s function-mapping table, and `openapi.yaml`'s entries paths. The one real gap is in the sync-badge derivation (AD-9/AD-10): it names only two of the three inputs the 3-state badge actually needs, so as written it cannot distinguish "Synchronized" from "Synchronization error."

## Findings

1. **AD-9/AD-10 sync-badge derivation is missing its third input — real gap.**
   - Backend fact (`sync-badge.md`): the badge has 3 states — *Synchronizing* (local write not yet confirmed), *Synchronization error* (the write was attempted and **failed** — network or one of the 13 taxonomy codes — and hasn't been reconciled), *Synchronized* (last confirmed write matches, nothing pending). The server exposes exactly two fields (`serverRevision`, `updatedAt`); everything else is inferred client-side.
   - Spine's claim: AD-10's rule is "one derivation function ... computed from `Entry.serverRevision` + `Entry.updatedAt` + the transient pending-write flag (AD-9)." AD-9 defines only one transient flag, "the only client-side 'pending write' state," feeding "AD-10's `Synchronizing` badge state."
   - Why it matters: those three inputs (two server fields + one pending flag) can only ever distinguish two states — pending vs. not-pending. Nothing in AD-9 or AD-10 introduces a transient *failure* signal, so there is no defined input that would ever flip the badge into the *Synchronization error* state once a write fails. The spine documents 2 of the 3 states' data sources and silently drops the third. A build unit following AD-9/AD-10 literally has nowhere to stash "this write failed and hasn't been retried" — it would have to invent that state itself, which is exactly the inconsistency AD-10 says it's preventing ("two screens computing ... differently").
   - Fix direction: AD-9 should define a second transient, in-memory, per-entry signal (e.g. a `pendingFailure`/last-`Failure` flag, cleared on next successful write or explicit retry) alongside the pending-write flag, and AD-10's derivation rule should list three inputs, not two.

2. **Error envelope's `requestId` field is unmodeled — minor gap.**
   - Backend fact: `openapi.yaml`'s `Error` schema has four properties — `code`, `message`, `retryable`, and `requestId` (optional, not in `required`) — in addition to the 13-code enum.
   - Spine's claim: AD-3's Failure hierarchy and the "Errors" row in Consistency Conventions only carry the `retryable` flag and the code identity; `requestId` is never mentioned anywhere in the spine (not in `Failure`, not in logging/observability conventions, which don't exist as a topic in the spine).
   - Why it matters: low severity since it's optional and nothing in `requirements.md` demands support-ticket correlation, but if any future debugging/support flow wants to surface the server's `requestId`, there is currently no field on `Failure` to carry it, and a build unit would have to decide ad hoc whether to add one — a small instance of the exact "two features inventing different shapes" problem AD-3 exists to prevent.

3. **Confirmed correct (no finding, stated for completeness): AD-5 URL/header policy.** Verified against every one of the 23 operations in `openapi.yaml`: exactly 3 carry `security: []` (`auth-signup`, `auth-login`, `auth-refresh`) and the remaining 20 carry `security: [bearerAuth: []]`, matching AD-5's "three `security: []` operations (signup, login, refresh) ... every other (`bearerAuth`) operation" exactly, with no endpoint miscategorized.

4. **Confirmed correct (no finding): AD-3/AD-4 Failure hierarchy and retry list.** AD-3's 13 named subtypes map 1:1 to `error-taxonomy.md`'s closed 13-code list (plus the correctly-scoped local `MalformedResponse`), and AD-4's 6 `retryable:true` codes (`NETWORK_TIMEOUT`, `NETWORK_OFFLINE`, `PII_CHECK_FAILED`, `EMBEDDING_FAILED`, `AI_GENERATION_TIMEOUT`, `RATE_LIMITED`) and the implied 7 `retryable:false` codes match the taxonomy table exactly — no code missing, extra, or renamed in a way that changes identity.

5. **Confirmed correct (no finding): AD-11 entry immutability.** Verified directly in `openapi.yaml`: the only `patch`/`delete` operations in the whole contract are `PATCH /account/settings` and `DELETE /account`; there is no `PATCH`/`DELETE /entries/{id}`. AD-11's claim ("`EntriesRepository` exposes create and read operations only ... matching the backend's lack of `PATCH`/`DELETE /entries/:id`") holds.

6. **Confirmed correct (no finding): Structural Seed deployment diagram.** Shows one Supabase Edge Function per operation (no REST router) and routes both Claude and Voyage AI strictly behind the Edge Functions layer, with explicit "never calls directly" arrows from the app to both providers — consistent with the backend docs' Edge-Functions-per-operation model and the cloud-only/no-direct-AI-access policy.
