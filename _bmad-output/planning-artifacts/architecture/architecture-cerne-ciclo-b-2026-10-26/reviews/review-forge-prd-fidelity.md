# Review: ARCHITECTURE-SPINE.md fidelity to forge session and PRD/addendum

**Verdict: real gaps.** The spine correctly carries forward every forge "(lock)" *package name* and the one scoped Hive→hive_ce correction, and it correctly avoids inventing a deadline. But at least two forge "(lock)/(kill)" rejection-rationales never made it into an enforceable AD-level Rule (they survive only in the memlog or a bare comment), one addendum-flagged integration risk was silently dropped, and three of the four PRD open questions this review was told to check are missing from the Deferred section entirely.

## Findings

1. **Cache "no relational engine" constraint has no AD-level Rule — only a memlog line and a code comment.**
   - Source fact (forge memlog, `(lock)` line 10): "No relational engine: nothing client-side ever filters, joins or sorts the cache — every query dimension (source/dateFrom/dateTo, semantic search) is server-owned." The forge doc restates this in its own body (`forged-idea.md` line 7) and explicitly rejects two counter-scenarios (local secondary sort on My Records, client-side dashboard fallback aggregation) as scope creep.
   - Spine's claim: AD-9 ("Cloud-only: no offline write queue") only says reads "transparently fall back to the local `hive_ce` cache" — it never states the client must not filter/join/sort that cache. No other AD (1–13) states it either. The only places this constraint survives are the spine's own `.memlog.md` (line 19/20) and a bare inline comment in the Structural Seed (`cache/ # hive_ce boxes: entries, chat_messages, chat_sessions + cursor`).
   - Why it matters: the Capability → Architecture Map row for "RF06 — semantic search/filter" cites only AD-9 and AD-12 — neither carries this rule. A future unit builder reading only the binding spine document (not the memlog) has nothing stopping them from adding client-side filter/sort logic against the Hive cache, which is exactly the scope-creep the forge session deliberately killed.

2. **Vault's rejection rationale and "zero Either/Failure plumbing" bedrock fact have no AD; the richer addendum detail (OS-level lockout handling) is entirely absent.**
   - Source fact (forge memlog `(kill)`, line 11 and `(note)` line 23; `addendum.md` "Security" section): rejected `biometric_storage` because gating storage behind biometric success can't satisfy the no-lockout PIN fallback; vault stays "100% local with zero Either/Failure plumbing." The addendum adds a materially more specific mechanism not present in the forge memlog at all: repeated biometric failures can trigger an **OS-level lockout** clearable only by the device passcode (not the app's PIN), which the app cannot programmatically reset — so the app must *detect that lockout state* and route to its own PIN fallback rather than keep retrying against the OS.
   - Spine's claim: the Capability → Architecture Map row for RF03 says only "`features/vault/` | AGENTS.md vault policy (local-only, zero `Either` plumbing)." AGENTS.md (the actual project instructions file) contains no vault-specific policy and no "zero Either plumbing" language — that phrase originates from the forge memlog's own note, not AGENTS.md, so the citation misattributes its source. There is no AD-N for the vault at all (every other locked forge decision got one: AD-3/4/5/8/9/10/11/12/13). The word "lockout" does not appear anywhere in `ARCHITECTURE-SPINE.md` or its `.memlog.md`.
   - Why it matters: this OS-lockout-detection behavior is the single most detailed piece of RF03 behavioral rationale in the source material (forge + addendum combined), and it is the reason `biometric_storage` was rejected in the first place. It didn't survive into the spine as a cross-unit invariant at all, only as an unenforced table citation.

3. **Addendum's "Open risk (not a decision)" — dio + flutter_secure_storage + get_it not pre-verified together — is silently dropped.**
   - Source fact (`addendum.md`, line 30): "the combination of `dio`, `flutter_secure_storage`, and `get_it` has not been pre-verified together; this is a flagged, accepted risk to resolve during F000's build, not a settled fact."
   - Spine's claim: no mention anywhere in `ARCHITECTURE-SPINE.md`'s Deferred section or its `.memlog.md`. The spine's Deferred section *does* carry forward other similar forge/addendum-level "open" items (env-loading mechanism, fvm pin, dashboard cache-invalidation) — so the omission of this one specific, explicitly-flagged integration risk looks like a silent drop rather than a considered decision not to carry it.
   - Why it matters: Deferred is exactly where an accepted-but-unverified cross-package risk belongs so F000's builder knows to smoke-test it; without it, the risk simply disappears from the record.

4. **Three of four named product-level PRD OQs are missing from the Deferred section — not resolved, but not surfaced either.**
   - Source fact (`prd.md` §8): OQ-2 (signup field set, blocks F000 — build unit 1), OQ-3 (tab-switching mid-capture in the Insertion Modal, blocks RF01 — build unit 3), OQ-6 (no retry affordance on the Sync Badge error state, blocks RF07 — build unit 5), OQ-7 (combined search+filter, blocks RF06 — build unit 6).
   - Spine's claim: the Deferred section surfaces only OQ-7 ("Combined search + filter interaction semantics... flagged as an open PRD question"). OQ-2, OQ-3, and OQ-6 appear nowhere in `ARCHITECTURE-SPINE.md` or its memlog.
   - Why it matters: the spine correctly never *silently decides* any of these (no AD secretly resolves signup fields, mid-capture tab-switching, or sync-badge retry), so it passes the "don't overreach" half of the check. But it fails the "surface it" half for 3 of 4 — especially OQ-6, which sits directly on top of AD-10 (the sync-badge derivation rule): a future reader of AD-10 has no signal that the badge's error-state retry affordance is still an open product decision. OQ-3 is similarly adjacent to AD-12's explicit carve-out of RF02's capture state machine, since tab-switching mid-capture could change that state machine's shape.

5. **Correctly handled — flagged here only for completeness, not a gap.** The Hive → hive_ce correction is scoped correctly: the memlog's CORRECTION entry explicitly preserves the 3-box shape, the cursor string, and the "no filter/join/sort" rule (even though, per finding 1, that rule itself never made it into an AD). The currency check was also not Hive-only — every other forge-session package pick (flutter_bloc, go_router, dio, get_it, fpdart, freezed, json_serializable, mocktail, fl_chart, local_auth, flutter_secure_storage) has its own dated pub.dev verification line in the spine's memlog, so there's no second missed-staleness check hiding elsewhere in the forge doc's package list.

6. **Correctly handled — flagged here only for completeness, not a gap.** The Deferred section's CI/CD note ("no CI tool... and no project deadline is stated anywhere in the input package... Revisit once a submission/demo deadline exists") correctly mirrors the PRD's own framing (§8 OQ-1: "No project timeline, deadline, or defense date is stated anywhere") without inventing one, consistent with the PRD's solo-author/TCC-capstone audience note.
