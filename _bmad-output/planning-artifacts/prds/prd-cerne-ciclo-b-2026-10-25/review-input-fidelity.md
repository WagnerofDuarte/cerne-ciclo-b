# Input-Fidelity Review — Cerne PRD

## Preamble
Checked all 43 FRs against `requirements.md` §1/§12, endpoint coverage against `backend/README.md` + `openapi.yaml`, AGENTS.md hard constraints, and visual/IA claims against `prototype-extract.md`. Overall fidelity is strong — delivery order, extension-feature non-goals, error taxonomy, and AI-provider/on-device-STT constraints all match the frozen sources exactly — but the polish passes introduced a few small, source-unsupported technical claims and dropped one explicitly-documented prototype behavior.

### Findings
- **high** Dropped "Salvar só a foto" OCR-failure fallback (§4.4 FR-13, prd.md) — `prototype-extract.md` §2.3 and §4 ("Asynchronous processing — photo OCR") explicitly document a second recovery path on OCR failure: a "Salvar só a foto" action that saves the Entry without extracted text, distinct from "Tentar novamente." FR-13's consequences only mention "error with retry, photo never discarded" — the save-without-text exit is absent, so acceptance testing would miss a documented state. *Fix:* Add a consequence to FR-13: "On OCR failure, in addition to retry, the user can save the Entry with no extracted text ('Salvar só a foto')."
- **medium** Unsupported reinstall caveat on biometric preference (§4.2 FR-7, prd.md) — FR-7 states the biometric toggle "survives app restarts (but not reinstalls)," but requirements.md §6.1 and the FR itself say the preference is stored server-side via `PATCH /account/settings`; a server-side value is retrieved on re-login after reinstall, so the "not reinstalls" claim is unsupported by (and in tension with) the cited mechanism. *Fix:* Remove the reinstall caveat, or replace with an `[ASSUMPTION]` tag if a specific client-side caching behavior is intended.
- **medium** New Chat Session creation's offline restriction dropped (§4.7 FR-25/FR-27, prd.md) — requirements.md §6.3 states `POST /chat/sessions` is "blocked offline" (distinct from `GET /chat/sessions` and message history, which work offline from cache). FR-27 ("Offline composer lock") only covers disabling the message composer in an existing conversation; FR-25 ("New-conversation action") has no offline consequence, so the PRD doesn't carry forward that starting a *new* session is also blocked while offline. *Fix:* Add a consequence to FR-25 or FR-27 stating that `POST /chat/sessions` is blocked offline, consistent with the existing-conversation composer lock.
- **low** Overstated citation on session-expiry overlay coverage (§4.1 FR-2, prd.md) — FR-2 says the overlay can appear on the timeline (RF07) or chat (RF04), "the two surfaces explicitly called out in requirements.md as session-dependent." Only RF07 explicitly states this in requirements.md text (§1, RF07 acceptance criteria); the chat case is sourced from `prototype-extract.md` ("Tela 1 — Sessão expirada," §4), not from requirements.md's RF04 text. *Fix:* Reword to cite both sources correctly, e.g. "...the timeline (RF07, called out explicitly in requirements.md) and chat (shown as the 'Sessão expirada' state in prototype-extract.md)."
- **low** Prototype/backend conflict on profile editing not flagged (§4.11 FR-41, prd.md) — `prototype-extract.md` §2.6 describes the avatar area as having "editable name/e-mail" inline. `openapi.yaml`'s `PATCH /account/settings` explicitly rejects email changes ("email is rejected"; request schema has no `email` property). FR-41 correctly scopes itself to display-name editing only, but — unlike the sync_status and error-taxonomy conflicts the addendum already documents under "Corrections carried forward" — this prototype/backend conflict is never called out, so a future reader could reintroduce an email-edit field by trusting the prototype literally. *Fix:* Add a line to addendum.md's "Corrections carried forward" noting that the prototype's visual "editable e-mail" affordance is not buildable — the backend's `account.settings.update` contract rejects email changes — and FR-41 deliberately omits it.
