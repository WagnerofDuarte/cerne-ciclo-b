## Findings

### New — currently-live findings, most severe first

1. **`PendingEntryWriteTracker` is never cleared at any session boundary — the most severe finding in this entire retrospective sweep.** It is a DI-singleton holding, in memory, the full plaintext `content` of every in-flight or failed capture (`pending_entry_write.dart:74`), shared across `TextEntryCubit`/`AudioEntryCubit`/`PhotoEntryCubit` and surfaced through `MeusRegistrosCubit`. `AccountSettingsCubit._finishSession()` — the only place any session-ending cleanup happens — calls `EntriesRepository.clearLocalCache()`/`ChatRepository.clearLocalCache()` (Epic 3's own fix target) but never touches the tracker; `sl.reset()` is confirmed, by repo-wide grep, to never run from any production code path. *Consequence — three distinct, confirmed mechanisms*: (a) User B's "Meus Registros" shows User A's still-pending or failed entry as a phantom card, exposing User A's actual private journal text — the app's core sensitive content — to User B; (b) if User A's write resolves successfully after User A has already logged out, `PendingEntryWriteTrackerImpl._resolve()` broadcasts it and `MeusRegistrosCubit._onEntryConfirmed()` permanently prepends it into **User B's** own list; (c) if User B taps the stale error badge's retry affordance, it replays `_repository.create()` with **User A's original content** — `EntriesRemoteDataSource.create()` takes no explicit user id and relies purely on the ambient Authorization header for whichever session is currently active, so this writes User A's journal content to the backend **as a new entry on User B's account** — a genuine cross-account content-injection path, not merely a display glitch. — **adversarial lens**; directly extends Epic 3's own action item 1 (which proposed the same session-boundary wiring for the two repository caches) — this tracker needs the identical treatment.
2. **`EntriesRemoteDataSource.list()`/`search()` have no per-item parse isolation — unlike every other decode path in this same feature.** `data.map((item) => EntryDto.fromJson(...)).toList()` is one expression inside one try/catch spanning the whole page; one malformed item (a null/missing field, or a `source` value the client doesn't yet recognize) discards every already-parsed item in that page. `entry_date_group.dart` and `EntriesRepositoryImpl`'s own Hive-cache paths already skip one corrupt item rather than failing outright (documented RNF09 rationale) — this inconsistency is specific to the two remote-fetch paths. *Consequence*: `Failure.malformedResponse` isn't one of the two types the offline fallback absorbs, so this surfaces as a hard error on the first page or a permanently-poisoned cursor on `loadMore()` — one bad entry anywhere in a page hides every otherwise-good entry on it, forever, since retrying re-fetches the same page. — **edge-case-hunter**
3. **A tempId-keyed detail view for a still-pending entry shows "Registro não encontrado" immediately and never self-corrects.** `EntryRecordCard`/`MeusRegistrosScreen` explicitly route a pending placeholder's synthetic tempId into the same `onCardTap`→`getById` path "with no branching." Since the tempId was never registered server-side, `getById` always resolves `NotFound`. `EntryDetailCubit` never subscribes to `_tracker.confirmedWrites`, so even if the real write confirms moments later while the screen is still open, nothing re-fetches or corrects the displayed state. *Consequence*: a user who taps a "Sincronizando" card is shown a misleading not-found message for content that may well succeed within moments, with no self-correction short of backing out and re-opening the (now different, server-id-keyed) card. — **edge-case-hunter**
4. **`EntryDetailCubit`'s `pendingWrites` subscription only mutates a field — it never calls `emit`.** Contrasted directly with the same class's `_onSessionStatusChanged`, which does call `emit` on every tick. *Consequence*: if a user opens the detail view of an entry already showing a `synchronizing`/`error` badge, and that write's status subsequently changes while the screen stays open, the badge is frozen at whatever it was when `load()` last ran — it never flips to "Sincronizado" or an error — until the user navigates away and back. Compounds finding 3: even once finding 3 is fixed to re-fetch on confirmation, this gap means any status change *before* a full re-fetch triggers still renders stale. — **verification-gap**
5. **`PendingEntryWriteTrackerImpl.create()` drops every existing failed write tracker-wide, not just the one it's replacing.** The code's own comment justifies this only for the single-modal, same-attempt retry case, but `_pending.removeWhere((_, write) => write.status is PendingEntryWriteFailed)` sweeps *all* failed records regardless of lineage — and since the tracker is one lazySingleton shared across Texto/Áudio/Foto, a failed text entry is silently wiped the moment the user later records an unrelated photo or audio entry. Since the tracker is purely in-memory, the original content is then unrecoverable. *Consequence*: a previously-failed entry's error card vanishes from Meus Registros with no warning and no way to retry it, the instant an unrelated capture is attempted. — **edge-case-hunter**; escalates `deferred-work.md`'s spec-4-2-round-2 entry (which framed this as a product question about lineage-scoping) with concrete cross-cubit evidence that makes it a correctness bug, not just an open design question.

### Already known, escalated to fix-now on new evidence

6. **`MeusRegistrosCubit.loadFirstPage()`'s failure branch silently swallows a real load error whenever a pending write exists**, emitting an empty `MeusRegistrosLoaded` instead of `MeusRegistrosError` — no message, no "Tentar novamente," and any previously-displayed entries are already gone from state (every `loadFirstPage()` emits `MeusRegistrosLoading` first). `deferred-work.md`'s spec-4-3 entry already flags this, found independently by two review layers, as "a plausible real data-loss-looking UX regression" — still unfixed and unexercised by any test combining a pending write with a failing reload from an already-loaded state.
7. **"Criar primeiro registro"'s CTA has no debounce/in-flight guard** — a rapid double-tap opens two stacked Insertion Modal instances. `deferred-work.md`'s spec-4-3 entry notes this reproduces the identical, already-shipped, unguarded pattern on the Home/Chat FAB, and recommends fixing both call sites together.

Process lessons:

- **A tracker/service holding sensitive in-memory state needs session-boundary cleanup audited at the same time its owning repository's cache-clear is fixed, not as a separate afterthought.** Epic 3's own retro proposed the cache-clear fix for `EntriesRepository`/`ChatRepository`; `PendingEntryWriteTracker` is a sibling DI-singleton added one epic later holding equally sensitive data, and nothing cross-checked whether the same fix needed to cover it too. When fixing a session-boundary gap, grep for every other DI-singleton in the same feature area before considering the fix complete.
- **A deferred item framed as "a product question, not a bug" should be re-examined once a second, more severe consequence of the same code is found.** Finding 5 (tracker-wide failed-write drop) was originally filed as a spec-interpretation question; the edge-case-hunter lens's cross-cubit framing turns it into a straightforward data-loss bug. The lesson isn't that the original framing was wrong — it was a defensible call given what was known then — but that "accept as a product question" dispositions should be revisited whenever new evidence changes the severity, not left permanently closed.
