### New — seam and currently-live findings (visible only from the merged, now-8-epics-deep state)

Produced by three parallel lens passes over `lib/core/{network,navigation,di,widgets}` and `lib/features/auth/**`, cross-checked against source directly. Deduplicated where two lenses independently found the same defect (noted per item).

1. **Boot-time env validation only checks key presence, not emptiness.** `UrlBuilder` (`lib/core/network/url_builder.dart:16-20`) and `injection_container.dart:27-28` call `dotenv.get(...)` for `FUNCTIONS_BASE_URL`/`SUPABASE_ANON_KEY`, which throws only if the key is *missing* from `.env` — a `.env` with the keys present but blank (exactly `.env.example`'s own shape, `FUNCTIONS_BASE_URL=`) passes silently. *Consequence*: the app boots fully and only fails much later, far less legibly, inside `UrlBuilder.build`/dio — instead of at `main.dart`'s existing catch block, which already prints a friendly "copy .env.example and fill in real values" message purpose-built for exactly this case. — **found independently by edge-case-hunter (both keys separately) and adversarial lens**
2. **An empty-but-non-null access/refresh token is treated as "present."** `header_interceptor.dart:68-70` sends `Authorization: Bearer <token>` whenever `readAccessToken()` resolves non-null, with no `isNotEmpty` check; `auth_repository_impl.dart:57-64` likewise persists whatever `accessToken`/`refreshToken` strings a signup/login response carries with no non-empty validation before `saveSession`. *Consequence*: an empty-string token from either path is indistinguishable from "no token" at the interceptor, so the backend receives a syntactically-present empty bearer header instead of the request being treated as unauthenticated. — **edge-case-hunter**
3. **Non-idempotent auth POSTs are retried transparently.** `retry_interceptor.dart:74-77`'s `shouldRetry` has no concept of "this POST has no idempotency key and may have already taken effect" — `auth-signup`, `auth-login`, and `auth-refresh` are retried on `NETWORK_TIMEOUT`/`NETWORK_OFFLINE` exactly like any idempotent GET. A later commit (story 6.1) eventually excludes chat/export writes from retry the same way; auth's own writes were never given the same exclusion. *Consequence*: a signup whose response is lost to a timeout gets silently replayed with the identical email/password, surfacing a successful signup as a user-visible failure when the backend rejects the duplicate; worse, `auth-refresh`'s refresh tokens are typically single-use/rotating (`openapi.yaml:177`) — a timed-out-but-actually-successful refresh gets replayed with an already-consumed token, the backend returns `AUTH_INVALID`, and `SessionRepositoryImpl.restoreSession()` treats that as a confirmed-dead token and logs out a user whose session was in fact still valid. — **independently found by edge-case-hunter and adversarial lens (adversarial traced the refresh-rotation consequence)**
4. **No redirect away from `/reauth` once the session is genuinely re-authenticated.** `app_router.dart:97-114` has no case for "user is on `/reauth` and `SessionStatus` transitions from `expired` back to `authenticated`" — only forward transitions into `/reauth` are handled. *Consequence*: a user who successfully re-authenticates while on the placeholder reauth screen is stranded there despite being fully authenticated again. — **edge-case-hunter**
5. **Expiry overlay gives up permanently if the overlay context isn't mounted at the exact post-frame callback.** `expiry_overlay_host.dart:99-104`: if `overlayContext` is null when `expired` fires, `_onStatus` resets `_expiryOverlayShown = false` and returns — but `_onSessionExpired()` only emits `expired` on the transition *from* `authenticated`, so once `_lastStatus` is already `expired`, nothing re-arms this path for the rest of that expiry episode. *Consequence*: a race with a Navigator rebuild can leave a user on an authenticated-looking screen with an actually-dead session and zero visual indication, until a manual restart. — **found independently by both edge-case-hunter and adversarial lens (the strongest-corroborated finding in this retro)**
6. **`AuthCubit` has no in-flight-submit guard on `toggleMode`/`emailChanged`/`passwordChanged`.** `auth_cubit.dart:32-63`: none of the three checks `state.isSubmitting` before mutating state. *Consequence*: editing a field or toggling mode while a submit is in flight applies the submit's eventual result (success/error, password-clear) on top of state the user already changed, producing a visibly mismatched mode/email/password. — **edge-case-hunter**
7. **`AuthCubit` is the one cubit in its DI module registered without a `dispose` callback.** `auth_injection.dart:35-48`: `SessionExpiryNotifier` and `SessionRepository` both get explicit `dispose:` callbacks specifically so `sl.reset()` closes their `StreamController`s; `AuthCubit` — itself wrapping a `StreamController` as a `Cubit` — gets none, inconsistent with the file's own stated convention. *Consequence*: every `sl.reset()` call (every test file's teardown) leaks one unclosed `Cubit` instead of releasing it. — **adversarial**
8. **`AuthState.toString()` interpolates the raw password field.** `auth_state.dart:101-104`: `'AuthState(mode: $mode, email: $email, password: $password, ...)'`, re-emitted on every keystroke via `passwordChanged`. *Consequence*: latent today (nothing calls `toString()` on a transition), but the moment any future `BlocObserver`/log line/crash reporter does — a near-universal Flutter debugging pattern — the user's plaintext password starts leaking into logs one keystroke at a time. — **adversarial**
9. **`BiometricReauthPlaceholderScreen` has no escape hatch, and the deferral that excused it has not held.** `placeholder_screens.dart:58-70` renders only a centered "Biometria" `Text` — no `AppBar`, no back arrow, no button — unlike every sibling placeholder, which reuses `_BackArrowHeader`. `deferred-work.md`'s spec-1-5 entry explicitly deferred this exact gap on the premise that "Epic 2's real biometric/PIN flow" would replace the screen — but Epic 2 (now shipped) built the app-*launch* vault/PIN gate, a different flow entirely, and never touched this mid-session-expiry placeholder. The deferral's assumed future owner did not materialize. *Consequence*: any user whose session actually expires mid-use and taps the expiry overlay's only button (`widget.router.go(AppRoutePaths.reauth)`) lands on a screen with zero interactive elements. — **adversarial, cross-checked against `deferred-work.md`'s spec-1-5 entry**
10. **`ConfirmationDialog.isOpen`'s deferred risk condition has now arrived.** `confirmation_dialog.dart:57`'s single process-wide static `isOpen` flag gates every `ConfirmationDialog.show()` call across the whole app. `deferred-work.md`'s spec-1-5 entry on this exact flag explicitly named its own trigger condition as "becomes reachable the moment a second consumer is added (Epic 8's account-deletion confirm, by the widget's own doc comment)" — Epic 8 has since shipped exactly that second consumer. *Consequence*: if either dialog's route is ever torn down without completing normally, `isOpen` sticks `true` and silently blocks the *other* feature's confirmation dialog app-wide (e.g., a stuck session-expiry overlay later blocking Epic 8's account-deletion confirm from ever showing), with no connection between the two obvious from either call site. — **adversarial, cross-checked against `deferred-work.md`'s spec-1-5 entry; reachability of the two consumers actually colliding was not independently re-verified against Epic 8's current call site in this retro**
11. **`dio_error_code.dart`'s mapping folds non-timeout, no-response exception types into the retryable `NETWORK_OFFLINE` code.** `dio_error_code.dart:19-32`: any `DioException` whose `type` isn't one of the four timeout/cancel types and whose `response` is null (e.g. `badCertificate`, `unknown`) falls through to `NETWORK_OFFLINE`. *Consequence*: a deterministic TLS/certificate failure — which fails identically every attempt — gets retried twice before surfacing, reported with the same "you appear offline" messaging as a real connectivity gap, burying a security-relevant signal. — **adversarial**
12. **A platform exception reading the stored access token is indistinguishable from "no token stored."** `header_interceptor.dart:53-67`'s `catch` around `readAccessToken()` treats any thrown platform exception the same as "nothing stored" — the request proceeds with no `Authorization` header, the backend returns an auth-failure code, and `ApiClient._mapDioException` unconditionally calls `notifyExpired()`. *Consequence*: a transient secure-storage glitch (plausible right after an iOS app resumes from background) is indistinguishable from an actually-dead session — the user sees the full "Sessão expirada" recovery overlay and is pushed to re-authenticate despite a session that was never actually invalid. — **adversarial**
13. **`restoreSession()`'s "never had a session" and "backend confirmed dead token" outcomes share the same `Failure` subtype.** `session_repository_impl.dart:130-139`: a fresh install / post-logout boot with no stored refresh token returns `left(Failure.authExpired(...))` — the identical subtype a backend-confirmed dead token produces a few lines below, even though the two events are semantically distinct. *Consequence*: latent today (nothing currently pattern-matches this `Left`'s subtype), but the first future consumer that does will fire "session expired" messaging on every fresh install, not just a real expiry. — **adversarial**
14. **`access_token_provider.dart`'s documented-safe save/clear ordering has no test covering a partial-write failure.** `saveSession()`/`clearSession()` each write/delete the refresh token before the access token specifically so a mid-sequence failure leaves the system self-healing on next boot (per the file's own code comment) — but every existing test (`access_token_provider_test.dart`, and the fake secure-storage channels in `session_repository_impl_test.dart`/`main_test.dart`) treats every write as unconditionally successful; none asserts call order or exercises a failure between the two writes. *Consequence*: a regression that swapped the write/delete order would not be caught by any existing test, and would, on a real partial secure-storage failure, cause an unwarranted forced logout (`saveSession`) or leave a dead token un-cleared (`clearSession`) instead of the self-healing the ordering exists to guarantee. — **verification-gap**
