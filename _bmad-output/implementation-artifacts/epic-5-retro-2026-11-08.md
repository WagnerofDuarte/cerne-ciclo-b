## Findings

### New — currently-live findings, most severe first

1. **`EntriesSearchCubit` is never cleared at any session boundary — the fourth consecutive epic in this sweep to surface this exact shape.** It is a DI `lazySingleton` (deliberately, so a query "survives leaving and re-entering `/meus-registros`") holding a live `Resource` of real search-result content (entry titles/snippets). `AccountSettingsCubit._finishSession()` clears only the entries/chat Hive caches (Epic 3's fix target) and, now, should clear `PendingEntryWriteTracker` (Epic 4's fix target) — it never touches this cubit, and `sl.reset()` is confirmed to never run from production code. `MeusRegistrosScreen.initState()` does call `updateFilters(source: null, ...)` unconditionally on every mount, but `updateFilters()`'s own "skip when unchanged" short-circuit treats the common no-filter case as a no-op, so User A's stale search results are never re-queried or cleared. *Consequence*: on a shared/handed-off device, a different account's real journal-entry content (titles/snippets returned by semantic search) renders directly to the next logged-in user — a cross-account privacy breach, the same shape as Epic 2's PIN finding, Epic 3's cache finding, and Epic 4's tracker finding, now confirmed a fourth time in a fourth consecutive epic. — **adversarial lens**
2. **The search box renders empty after a screen remount while the search surface keeps showing a stale, active search — a confirmed dead end, not just a cosmetic gap.** `EntriesSearchBar`'s `TextField` has no `controller`/`initialValue`; `MeusRegistrosScreen`'s teardown/rebuild (tab switch away and back, or navigating into entry detail and back — the plain `GoRoute` for `/meus-registros` tears down the whole subtree, acknowledged by the screen's own remount-skeleton-timer guard) discards the visible text but not the cubit's retained `Resource`/query. *Consequence*: the user sees search results (or a lingering error/skeleton) with an apparently blank, unused-looking search box, and no obvious way back to the plain timeline — the empty box has nothing to delete to trigger the documented "empty query reverts to timeline" recovery path, and "Limpar filtros" doesn't clear search either. — **independently found by both the edge-case-hunter and adversarial lenses**, and sharpens `deferred-work.md`'s own spec-5-1 entry (which flagged the stale-results-with-empty-box symptom but not that it's a genuine dead end) from "worth a look" to a confirmed bug.
3. **A fast-typing user can see a flash of stale search results for an already-abandoned query term.** `onQueryChanged` cancels and restarts the debounce timer on every keystroke but does **not** bump `_generation` — that counter only advances on clear-to-empty or inside `_search()` once a debounce actually fires. If query A's network call resolves before query B's fresh 300ms debounce elapses (plausible on a fast backend), A's result still passes the `generation != _generation` guard (unchanged) and renders — momentarily overwriting the screen with results for a term the user has already typed past. *Consequence*: contradicts the story's own "exactly one call, for the final value" guarantee at the display level; not covered by the existing "stale response" tests, which only exercise the case where the *second* query's debounce has already fired before the first resolves. — **edge-case-hunter**
4. **Superseded search requests are never actually cancelled — only their results are discarded.** No `CancelToken` exists anywhere in `ApiClient.get()`/`EntriesRemoteDataSource.search()`/`EntriesRepositoryImpl.search()`/`EntriesSearchCubit`. A fast-typing or rapid filter-toggling session (story 5.3's own immediate re-search-on-filter-change, no debounce) fires overlapping `entries-search` calls; the generation guard correctly drops the superseded *result*, but the request still runs to completion server-side. *Consequence*: given `openapi.yaml`'s own note that `entries-search` has "no server-side throttle," every superseded-but-not-cancelled search still triggers a full, billable embedding-generation call that is always discarded — a real AI-provider cost multiplier, directly in scope of the project's "every AI feature goes through the backend" cost accountability, not a correctness bug. — **adversarial lens**

### Confirmed clean (explicitly checked, worth recording as a negative result)

- **Retry-safety of `entries-search` is genuinely correct and genuinely tested.** It's a GET, correctly excluded from nothing (unlike the non-idempotent POSTs `RetryInterceptor` already excludes), and retrying it on `EMBEDDING_FAILED`/`RATE_LIMITED`/`NETWORK_TIMEOUT` is the intended policy (AD-4) — verified against `error-taxonomy.md`. A dedicated e2e test (`entries_search_flow_e2e_test.dart`) queues real repeated 503s through the real `RetryInterceptor` and passes. Out-of-order results from a slow retry chain are also safe: the generation guard is checked on every resolution regardless of retry duration.
- **The generation guard correctly discards a stale result racing a filter-clear**, confirmed by direct trace of every interleaving and backed by a dedicated passing test. The real desync in this area lives at the UI-state level (findings 2-3), not in the generation guard itself.
