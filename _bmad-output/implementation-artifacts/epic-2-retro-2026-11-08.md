## Findings

### New — currently-live findings

1. **Vault PIN is never cleared on logout or account deletion.** `VaultRepositoryImpl.submitPin` (`lib/features/vault/data/repositories/vault_repository_impl.dart:236-271`) writes the PIN under a fixed secure-storage key (`vault_pin`) on first use. `AccountSettingsCubit._finishSession()` (`account_settings_cubit.dart:405-407`), reached from both `logout()` and `deleteAccount()`, calls `VaultRepository.lock()` but never a PIN-clear; `SessionRepository.logout()` → `AccessTokenProvider.clearSession()` (`access_token_provider.dart:84-85`) only deletes the access/refresh token keys. No code path anywhere calls `delete(key: 'vault_pin')` (grep-confirmed: only `read()`/`write()` call sites exist). *Consequence*: the next account to use the device — a second user on a shared device, or the same user re-registering after deletion — inherits the previous account's PIN as its own vault secret, with no "forgot PIN" flow to recover. For account deletion specifically, this undercuts the LGPD-erasure promise the deletion dialog itself makes ("apagados para sempre, conforme a LGPD") — the deleted user's PIN persists as a live access-control secret after the account is gone. — **adversarial lens**; supersedes `deferred-work.md`'s existing "vault PIN never cleared on logout" entry (previously dispositioned as "ambiguous, not a defect" in Epic 8's own retro) with a concrete leakage/erasure mechanism.
2. **A PIN-submit timeout can be followed by a surprise unlock seconds later.** `VaultLockScreen._submitPin` wraps `vaultRepository.submitPin(pin)` in a 10s `.timeout()` (`vault_lock_screen.dart:182-184`) — but `Future.timeout()` only stops the caller from waiting; the underlying secure-storage read inside `VaultRepositoryImpl.submitPin` (`vault_repository_impl.dart:239`) keeps running. If it resolves correctly after the UI has already shown "Não foi possível verificar o PIN" and reset `_submittingPin`, the repository's own `_emit(VaultStatus.unlocked)` fires moments later with no further input from the user. *Consequence*: a user who saw a failure message and put the phone down believing it was still locked experiences a silent, unattended unlock. — **edge-case-hunter**
3. **An empty-string stored PIN is a permanent, unrecoverable lockout.** `submitPin` (`vault_repository_impl.dart:254,272-283`) only special-cases `storedPin == null` as "unset" — any other value, including `''`, is compared directly against the entered PIN, which `PinKeypad` always submits as exactly 4 digits and can therefore never equal. *Consequence*: if `_secureStorage.read` ever returns `''` instead of `null` for this key (a platform/plugin quirk, a corrupted keychain entry, any future code path that writes an empty value), the user is locked out of PIN entry permanently — no attempt cap, no reset screen exists. — **edge-case-hunter**
4. **The `biometricEnabled` preference is never reconciled against actual OS biometric capability.** Confirmed via `grep -rn "canCheckBiometrics|isDeviceSupported|getAvailableBiometrics" lib/` — zero matches anywhere in the app. `VaultLockScreen` unconditionally attempts `authenticate()` first whenever the stored preference is `true` (`vault_lock_screen.dart:85-88`), regardless of whether biometrics are still enrolled at the OS level. *Consequence*: if the user disables Face ID/Touch ID (or removes all enrollments) after leaving Cerne's own preference at `true`, every future `/vault` visit pays the latency cost of one guaranteed-to-fail native prompt before falling to PIN, and the stale preference never self-corrects unless the user manually revisits Configurações. — **edge-case-hunter**
5. **Two independent `fetchBiometricEnabled()` calls fire on every cold boot.** `main()` awaits one, bounded to 2s, specifically so `/vault`'s first build reads the right preference (`main.dart:40-43`); `CerneApp.initState()` then unconditionally fires a second, fire-and-forget call a few lines later (`main.dart:127-131`) with no check for whether the first already resolved. *Consequence*: not a correctness bug (the repository's own `_generation` guard makes the two calls race-safe — confirmed by the adversarial lens reading `account_settings_repository_impl.dart`), but every single cold start sends one unnecessary `PATCH /account/settings` round trip. — **adversarial lens**
