## Findings

### New — currently-live findings

1. **Every poll failure is treated identically regardless of whether it's actually retryable — a two-sided bug.** `ExportJobCubit`'s poll failure handler increments a single `_consecutivePollFailures` counter and gives up after 5, without ever reading `Failure.retryable`. *Consequence A*: a flaky connection spanning exactly 5 polls (~10 seconds at the 2s poll interval) permanently abandons a job that is almost certainly still alive and will finish successfully server-side — the sheet shows a generic failure with no retry affordance and no way to resume watching the same job id. *Consequence B*: a truly non-retryable failure (e.g. `AUTH_EXPIRED`, which also fires the global `SessionExpiryNotifier` → app-wide redirect to `/auth`) is *not* fast-failed either — the sheet keeps showing a spinner for up to 5 doomed polls while the rest of the app may already be navigating the user to the login screen underneath the still-open modal. — **edge-case-hunter**
2. **A job that finishes with zero actual records renders identically to a normal successful export — the seventh instance of this sweep's recurring "success but empty" implicit-third-state gap** (already found in Epics 1, 3, 4, 5, 6, and 8's own retrospectives). `ExportJobStatusDto`'s `entryCount` field is decoded but never consulted by `toState()` — its own doc comment explicitly notes this. If every entry in the requested period is deleted after the synchronous empty-period check passes at creation but before the async job finishes, the user gets an apparently-successful export (both download buttons live) that actually contains zero records, with no distinguishing message. — **edge-case-hunter**
3. **The export-summary-create network call has no loading indicator at all — a direct RNF01 violation.** `docs/input/requirements.md` states RNF01 as "any network call above 300ms shows a loading indicator." Between the date-range picker resolving and either the status sheet or an error appearing, `_onExportTap` awaits a real network call with zero visual feedback — `_ExportIconButton` is a plain stateless icon never wired to the in-flight state. On a slow connection, the tap looks dropped. Contrasts directly with the same screen's own `_skeletonTimer`/`_showSkeleton` handling for the entries list load, which this path doesn't reuse. — **edge-case-hunter**

### Lower-confidence findings (flagged, not confirmed bugs)

4. **An untested interaction between `ExpiryOverlayHost`'s imperative navigation and an open, polling export sheet.** If a mid-session expiry fires while the export sheet is open and the user taps "Entrar novamente," `router.go(AppRoutePaths.reauth)` runs while the sheet (a pageless route on the same Navigator) is still open with a live poll `Timer`. This relies on Flutter/go_router's documented page-removal-cascades-to-pageless-routes behavior to tear the sheet down correctly — almost certainly correct, but genuinely untested anywhere in the suite. A regression in that Navigator behavior (a future Flutter/go_router version, or a nested-navigator refactor) would ship silently. — **adversarial lens**
5. **A download failure that resolves after the sheet is already dismissed has nowhere to surface — by design, but unconfirmed as an accepted product gap.** `_download`'s `isClosed` guard is deliberately absent so a download started before dismissal can still complete; `ExportStatusSheet._handleDownload`'s own `context.mounted` check then silently drops the resulting SnackBar if it fires late. Worth a one-line product confirmation that this silence is intended, not merely assumed. — **adversarial lens**

### Confirmed clean (explicitly checked, worth recording as a negative result)

- **This epic does not add a sixth instance of the sweep's recurring session-boundary DI-singleton leak.** `ExportJobCubit` is deliberately `registerFactory` (explicitly following the "one-shot-cubit precedent" from `TextEntryCubit`), not a `lazySingleton` — a fresh instance per export tap, explicitly closed in every exit path of `_onExportTap` and by the status sheet's own `finally` block. The two true singletons in this feature (`ExportRepositoryImpl`, `ExportRemoteDataSource`) are confirmed stateless pass-throughs with no per-user cache (doc comment: "no cache, AD-15"). This is the first epic in this sweep's 2-7 run to structurally avoid the pattern rather than add a new instance of it.
- **Retry/polling lifecycle is correct.** `export-summary-create` is correctly excluded from `RetryInterceptor`'s non-idempotent-write list; the two GETs (`export-status-get`, `export-download-get`) are correctly not excluded; `AUTH_EXPIRED` detection on the download-redirect call routes through the same shared mapping as every other endpoint; the poll `Timer` is cancelled on every terminal state and after 5 consecutive failures (even though finding 1 shows that threshold logic itself needs fixing); reentrancy is guarded so two `getStatus` calls can never race for one cubit instance. Verified both by direct reads and by the full real-Dio/real-Timer `export_flow_e2e_test.dart` suite passing.
- **The core UX guards hold up**: double-tap on the export icon and on each download button are both correctly guarded; the 5 job/narrative states are visually distinct, so loading/empty/errored aren't confused at that granularity (though finding 2 shows one specific success-shaped state isn't distinguished from a different kind of "empty").

### Verification gaps (behavior correct today, unguarded against regression)

6. **A mid-flight `close()` during an in-progress poll's `getStatus` call is untested** — the only mid-flight-close test in the suite covers `_download`, not `_poll`. If the `isClosed` guard in `_poll()` ever regressed, `emit()` on an already-closed cubit from inside a `Timer` callback would go uncaught by any test.
7. **A mid-flight `close()` during `start()`'s `createJob` call is untested, and the test fake has no delay hook to even construct the race** — unlike `getStatus`'s `delayNextGetStatus` gate, `createJob` has none.
8. **`meus_registros_screen.dart`'s `!mounted` guards during the export flow are never tested via an actual unmount.** If the guard responsible for closing a freshly-created `ExportJobCubit` when the screen disappears before the sheet opens were ever broken, a live `Timer.periodic` poll loop would leak and run forever in the background with no test catching it.

Process lessons:

- **This epic is the sweep's first positive counter-example to the recurring session-boundary pattern, and it's worth understanding why it succeeded.** `ExportJobCubit` was deliberately scoped as a factory from the start, following an explicit named precedent (`TextEntryCubit`'s "one-shot-cubit" pattern) rather than defaulting to a singleton the way `ChatCubit`/`EntriesSearchCubit`/`PendingEntryWriteTracker` each did. The lesson for any future epic introducing a new cubit/service that holds per-request or per-user state: default to factory-scoped-and-explicitly-disposed unless there's a specific, named reason (like `EntriesSearchCubit`'s "survive navigation" requirement) to use a singleton — and when a singleton is chosen for that reason, that's exactly the signal to also wire it into the session-boundary cleanup this sweep has been asking for since Epic 3.
