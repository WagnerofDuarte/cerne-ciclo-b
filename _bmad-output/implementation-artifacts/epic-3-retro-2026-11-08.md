## Findings

### New — currently-live findings

1. **Journal/chat local caches are only cleared on the two explicit logout/delete-account buttons — not on the far more common silent session-expiry or fresh-login path.** `EntriesRepository.clearLocalCache()`/`ChatRepository.clearLocalCache()` are invoked from exactly one place, `AccountSettingsCubit._finishSession()` (`account_settings_cubit.dart:405-417`), reached only via "Sair"/"Apagar conta" — grep-confirmed as the only two call sites app-wide. `SessionRepositoryImpl.restoreSession()`'s `AuthExpired`/`AuthInvalid` branch (a dead refresh token discovered at boot — the typical way a session ends after days of inactivity) clears only the secure-storage tokens, never the entries/chat caches; `AuthCubit.submit()`'s login/signup path has no cache-clear step either. `EntryDto` carries no user/account identifier at all, so nothing downstream can filter stale rows even if it tried; the shared `Box<Map>` entries box is opened once for the app's lifetime and never `clear()`'d on a fresh authenticated session. *Consequence*: on a shared/family device, a different account's cached journal entries and chat history persist and can surface — `EntriesRepositoryImpl._offlineFallback()` dumps the *entire* box (a mix of both accounts' content) into `MeusRegistrosCubit`'s list if the new account goes offline before its first successful online fetch. This is the direct analog of Epic 2's vault-PIN-never-cleared finding, but reaches more sensitive content (actual diary/chat content, not just an access-control secret) through the more common session-ending path. The original risk `deferred-work.md`'s spec-3-1 entry (lines 137-138) flagged as "becomes exploitable once a logout feature ships" was only half-remediated when Epic 8 shipped logout. — **adversarial lens**
2. **Story 3.4's own "cancel-safe capture across all tabs" claim does not cover swipe-to-dismiss or scrim-tap dismissal, for any tab.** `InsertionModal.show()`'s `showModalBottomSheet` call (`insertion_modal.dart:80-97`) passes no `isDismissible`/`enableDrag` override, so Flutter's built-in swipe-down and barrier-tap gestures bypass the `isSaving`-gated "x" button and tab bar entirely — on either gesture, the sheet pops immediately and `show()`'s `finally` block runs each cubit's `cancel()`/`close()` concurrently with any in-flight `_tracker.create()` call, for Texto, Áudio, or Foto alike. `deferred-work.md`'s spec-3-1 entry (lines 143-144) documented this gap but scoped it only to the Texto tab; story 3.4 — whose whole stated purpose is extending cancel-safety to every tab — never actually extended this specific guard to any of them, including the one it was already known for. *Consequence*: confirmed not to be data loss (`PendingEntryWriteTrackerImpl.create()` resolves and broadcasts independently of the cubit's lifecycle), but the user sees the modal vanish mid-save with no "Registro salvo" confirmation for a save that, in fact, succeeded. — **found independently by both edge-case-hunter and verification-gap lenses**
3. **`AudioEntryCubit` has no app-lifecycle awareness at all, unlike the project's own established precedent.** No `WidgetsBindingObserver`/`didChangeAppLifecycleState` exists anywhere in `lib/features/capture`, while `VaultRepositoryImpl` already uses exactly this pattern for its own idle-timeout/re-lock logic. Backgrounding the app mid-recording or mid-transcription (no `UIBackgroundModes` audio entitlement is declared in `Info.plist`) leaves the Dart-side `AudioRecording` state and its elapsed-seconds timer presenting a live UI with no awareness the native session may have been interrupted by the OS. *Consequence*: on return to foreground, the user has no indication anything went wrong until they tap stop, at which point a generic "Não foi possível gravar o áudio" surfaces with no differentiated messaging. Not independently verifiable without a device (AGENTS.md), but the missing hook itself — contrasted with `VaultRepositoryImpl`'s precedent — is a verified gap in the current source regardless of exact on-device behavior. — **edge-case-hunter**

### Verification gaps (behavior correct today, unguarded against regression)

4. **Cancel racing an in-flight save is untested for both `AudioEntryCubit` and `PhotoEntryCubit`.** `cancel(discardPreserved: true)` deletes the recording/photo file unconditionally; every existing "discardPreserved" test reaches its target state via `stopRecording()`/`pickFromCamera()` alone, never via `save()` first — so the actual race (cancel firing while `_tracker.create()` awaits) is never driven concurrently. — **verification-gap**
5. **`WhisperAudioTranscriber`'s documented assumption that `transcribe()` itself never throws is untested** — only `downloadModel()` throwing is covered; `transcribe()` throwing would propagate uncaught instead of degrading to the documented null/error path, and the suite would still pass. — **verification-gap**
6. **`RecordMicRecorder.cancel()`'s best-effort delete-failure catch branch is never exercised** — every existing test pre-creates the file so the delete always succeeds; a narrowed/removed catch would go uncaught by any test. — **verification-gap**
7. **`PhotoEntryCubit`'s DI factory-registration distinctness (fresh instance per "+" tap) is never verified**, unlike the equivalent checks that already exist for `TextEntryCubit`/`AudioEntryCubit` in `bootstrap_integration_test.dart`. A regression to `registerLazySingleton` would surface only on a real device. — **verification-gap**

### Already known (recorded during the epic's own story-level reviews; not re-routed)

This epic's own story-level reviews already caught and documented an unusually high number of races/leaks in the capture cubits — confirmed still present at the cited lines, not newly discovered:

- `AudioEntryCubit.cancel()`'s unconditional `_stopping = false` reset can clobber a concurrently-live `stopRecording()` call's own flag in a narrow hung-native-call interleave (`deferred-work.md`, spec-3-3 round 3) — **re-confirmed present** by the edge-case-hunter lens at the current cited lines; still the same accepted low-severity gap (requires a hung native `stop()` plus precise interleaving).
- `whisper_ggml`'s in-flight `transcribe()` call cannot be cancelled when the user switches tabs mid-processing (`deferred-work.md`, spec-3-2) — **re-confirmed present**; battery/CPU-only, no incorrect user-visible behavior since the result is dropped either way.
- No maximum recording duration enforced; `WhisperAudioTranscriber.transcribe()` calls `downloadModel()` on every invocation with no cached-already-downloaded short-circuit (both spec-3-2 entries) — still open.
- Camera/gallery permission denial conflated with a plain cancel in `PhotoEntryCubit` (spec-3-3) — still open, product/UX decision.
- Photos sent to `media-ocr` at full resolution, no client-side downscale (spec-3-3) — still open, accepted per the spec's own Never clause.
- `TextEntryCubit.save()`'s double-tap guard has no dedicated regression test (spec-3-1, surfaced during 3.2's review) — still open; the Texto-tab sibling of findings 4 above.
- Test-double duplication across capture test files, and round-2 findings duplicated verbatim between spec files and `deferred-work.md` (spec-3-3/3.4 entries) — still open, low-severity process items.
- `PhotoEntryCubit._pick()`'s fire-and-forget file-delete assumes `image_picker` never reuses a path across picks (spec-3-3 round 3) — still open, unverifiable without a device.
