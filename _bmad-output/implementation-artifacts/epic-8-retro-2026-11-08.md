### New — seam findings (visible only once all 5 stories' code coexists)

Produced by three parallel review-lens passes (adversarial, edge-case-hunter, verification-gap) over the final merged state of `account_settings_cubit.dart`, `account_settings_screen.dart`, `account_settings_repository_impl.dart`, `dashboard_cubit.dart`, `dashboard_narrative_cubit.dart`, `dashboard_chart_section.dart`, cross-checked against the 6-commit diff. Each item below was independently spot-verified against the source file before being kept (per-item note says what was checked).

1. **Narrative-error announce listener bypasses the dedup guard its sibling listener was given.** `account_settings_screen.dart`'s `BlocListener<DashboardNarrativeCubit, Resource<String>>` (narrative-triggered, added by spec-8-2's amendment) announces "narrativa indisponível" on every `ResourceError` emission with no dedup check. Its sibling `BlocListener<DashboardCubit, ...>` (dashboard-triggered, added one story later by a spec-8-4 review patch) was given a `_dashboardOverflowAnnounced` flag specifically to stop repeat announcements of the same unresolved error — but that flag is written only by the second listener; the first bypasses it entirely. *Verified*: read both listener bodies directly (lines ~525–602); confirmed the narrative-triggered listener has no reference to `_dashboardOverflowAnnounced`. *Consequence*: tapping "tentar novamente" repeatedly while the narrative keeps failing re-triggers a VoiceOver announcement on every tap — the exact spam the sibling fix exists to prevent, reachable through the other listener. — **adversarial lens**

2. **`clearStaleError()` never clears `deleteAccountErrorMessage`.** `account_settings_cubit.dart:278-282`'s `clearStaleError()` — written in spec-8-1/8.3 specifically so a DI-singleton cubit's leftover error text doesn't linger into an unrelated later screen visit — only clears the biometric-toggle `errorMessage` field. `deleteAccountErrorMessage` was added two stories later (8.5) and never got the same treatment; `initState()`'s single call site (`screen.dart:93`) only reaches the older field. *Verified*: read `clearStaleError()`'s body and its one call site; confirmed it checks only `state.errorMessage`. *Consequence*: after a failed "Apagar conta" attempt, leaving Configurações via the back arrow and returning later (no new attempt) still shows the stale deletion-failure message — the exact bug `clearStaleError()` was built to prevent, reproduced for the field added after it. — **independently found by both the adversarial and edge-case-hunter lenses**

3. **`deleteAccount()` is the only write method in `AccountSettingsRepositoryImpl` with no generation guard.** `setBiometricEnabled`/`setDisplayName` each capture `++_generation`/`++_nameGeneration` and discard a superseded result; `deleteAccount()` (`account_settings_repository_impl.dart:212-213`) is a bare pass-through with no counter at all, despite the class's own doc comment stating "every call captures the generation current at its own start" as its concurrency convention. *Verified*: `grep -n "_generation\|deleteAccount"` on the file — confirmed no counter touches the `deleteAccount` line. *Consequence*: the one new repository method this epic added quietly breaks the class's own stated invariant; a future reader who trusts "every write here is generation-guarded" is wrong specifically for the operation where getting concurrency handling wrong matters most. — **adversarial lens**

4. **`deleteAccount()` cubit method has `try`/`finally` with no `catch`.** `account_settings_cubit.dart:465-481`: if `_repository.deleteAccount()` or `_finishSession()` throws instead of resolving to `Either` (nothing currently does, but nothing enforces that — the same caveat `logout()`'s own `try`/`finally` patch already documents for itself), the exception propagates uncaught; `isDeletingAccount` resets via `finally`, but no error is ever shown. *Verified*: read the method body directly — confirmed no `catch` clause exists. — **edge-case-hunter lens**

5. **Dashboard aggregate's error card has no retry link; the narrative's does.** `dashboard_chart_section.dart`'s `_errorCard` (story 8.1) renders static text only; `_narrativeSection`'s `ResourceError` branch (story 8.2, same file) explicitly added a "tentar novamente" retry link for a failure of the identical shape. *Verified*: grepped both branches — confirmed no `GestureDetector`/`onTap` in `_errorCard`. *Consequence*: a user whose main chart fails to load has no in-screen recovery path, while the narrative directly below it does, for the same failure class. — **adversarial lens**

6. **"Apagar conta" shipped with the same missing-loading-indicator gap "Sair" already had — and didn't log the recurrence.** Spec-8-4's own review found and *explicitly deferred* "Sair" having no loading indicator while `isLoggingOut`. Spec-8-5 then added "Apagar conta" with the identical `onPressed: null`-only pattern and no indicator, and its own Review Findings section never mentions it. *Verified*: read both buttons (`screen.dart` ~614–667) — neither has a `CircularProgressIndicator`; `deferred-work.md`'s spec-8-5 entries contain no matching item. *Disposition*: the underlying gap is the same already-accepted tradeoff (shared `AppButton` primitive has no loading-slot API, no device to visually verify a layout change) — **accept as-is**, same rationale as "Sair"'s own deferral. The actionable lesson is process, not code: a later story reusing a pattern a prior story already deferred should cross-reference the existing deferral instead of leaving a second, unlinked instance of the same gap. — **adversarial lens**

7. **`_emptyCard`'s padding wasn't updated by the round-2 "no card-resize" fix that touched its siblings.** Story 8.1's round-2 review fix switched `_loadingCard`/`_errorCard`/`_populatedCard` to `DesignTokens.dashboardCardPadding` (20) specifically so the card wouldn't visibly resize across a loading→data transition — `_emptyCard` (the zero-entries state) was left on `DesignTokens.spacingLg` (24). *Verified*: `grep -n "dashboardCardPadding\|spacingLg"` on the file — confirmed `_emptyCard` at line 113 is the only card-builder still using `spacingLg`. *Consequence*: a first-time user with zero entries sees exactly the card-resize jump the fix was written to eliminate everywhere else. — **adversarial lens**

8. **Biometric-toggle and name-save spinners have no `semanticsLabel`; the dashboard's identical spinner does.** Story 8.1 gave the dashboard's `CircularProgressIndicator` an explicit `semanticsLabel` ("Carregando gráfico de evolução") as a dedicated accessibility fix. The two near-identical spinners already on the same merged screen (biometric `isSaving`, name-edit `isSavingName`) have none. *Consequence*: a VoiceOver user saving a name or toggling biometric login gets no spoken in-progress feedback, unlike the dashboard's own loading state on the same screen. — **adversarial lens**

9. **Narrative `ResourceData` with a blank/whitespace-only string is an unhandled implicit third state.** The render path (`dashboard_chart_section.dart`) already trims and suppresses a blank narrative string (a dedicated round-2 test covers this); but the two announce-listeners in `account_settings_screen.dart` only check `is ResourceError<String>` — a successful-but-blank response neither renders nor announces, silently falling through both paths. *Verified*: re-read both listener bodies; neither inspects `ResourceData.data` for blankness. Low severity (no crash, no visible defect — the card already handles this correctly), but a genuinely unhandled implicit branch. — **edge-case-hunter lens**

10. **`AccountSettingsCubit`'s one-time construction-time read of `currentDisplayName`/`currentEmail` depends on an unenforced boot-ordering assumption.** The cubit reads these fields exactly once, at DI-singleton construction; correctness depends on `main()`'s boot-time `fetchBiometricEnabled()` call having already resolved by the time something first resolves `sl<AccountSettingsCubit>()` — nothing asserts or enforces that ordering. *Disposition*: architectural risk, not a current bug (today's DI wiring satisfies the ordering) — **defer**, revisit if DI bootstrap ever changes (eager registration, splash prefetch, new test harness). — **adversarial lens**

11. **A failed boot-time `fetchBiometricEnabled()` leaves the name/email header permanently blank for the session.** `_currentDisplayName`/`_currentEmail` are populated only by piggybacking on a successful boot fetch or a successful `setDisplayName()` call; nothing retries if both of `main.dart`'s one-shot boot attempts fail (e.g., app opened offline). *Disposition*: real but narrow (requires offline app launch) — **defer**, propose retrying the fetch the next time Configurações opens rather than relying solely on the two boot-time attempts. — **adversarial lens**

Process lessons (what would prevent the next one — no action required unless a future epic recurs):

- **A later story adding a second guard/listener for a concern a prior story already partially solved should diff against the sibling, not just review its own new code.** Findings 1 and 8 are both this shape: a later story's accessibility/dedup fix was added without checking whether an earlier story's own near-identical control already needed, or already had, the same treatment. The per-story 4-layer review process is excellent at catching defects in a story's own diff; it has no step that asks "does a sibling control on this same merged screen already have this, or need this too?" — worth adding as an explicit check the next time a story extends an existing shared screen/cubit rather than building a new one.
- **A story that re-ships an already-deferred gap under a different name should log the recurrence, not leave it silent.** Finding 6 (spec-8-5 reproducing spec-8-4's own already-deferred "no loading indicator" gap without mentioning it) is low-impact here because the underlying disposition is correctly "accept as-is" either way — but the pattern is worth naming: a recurrence of a *known* gap is cheap to flag with one cross-referencing sentence and easy to miss silently once code review assumes "this is new, not a repeat."
- **Worth keeping, not fixing**: the human-routed spec-amendment path (Spec Change Log entries for stories 8.1 and 8.2) worked exactly as intended — two genuinely wrong pieces of *frozen, previously-approved* spec text were caught by post-implementation review, routed to the human via `AskUserQuestion` rather than silently patched or silently left broken, and resolved with an explicit, evidenced amendment plus a "KEEP" list protecting everything that was already correct. This is the retrospective's own job (catching what no single session could see) already happening *inside* the epic, one story at a time — the fact that two such catches were needed in one five-story epic is itself worth noting for anyone estimating how often frozen spec text needs this safety valve.
