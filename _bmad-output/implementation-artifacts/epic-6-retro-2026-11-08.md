## Findings

### New — currently-live findings, most severe first

1. **`ChatCubit` itself — not just its Hive cache — leaks a previous account's full chat content in memory, and the root cause is now identified: there is no production trigger for `sl.reset()` anywhere in the app.** `ChatCubit` is `registerLazySingleton`, living for the app's entire process lifetime; its `dispose: (cubit) => cubit.close()` only runs via `get_it`'s `sl.reset()`/`resetCoreDependencies()`, which grep confirms has **zero production call sites** — used only in test teardown. `ChatCubit.init()`'s own no-op guard (`if (state is ChatReady || isClosed) return`) means the next login's `ChatScreen.initState()` is swallowed silently, so the previous account's `ChatReady.messages` (actual chat content), `.sessions`, `_bookmarkStateByServerId`, and `_scrollOffsets` render as-is to whoever logs in next on the same device. This is strictly broader than Epic 3's Hive-cache finding — even if Epic 3's proposed fix (clear the cache on session-expiry/fresh-login) were implemented, it touches only Hive, never this cubit's in-memory state. *Consequence*: a cross-account content leak of the app's most sensitive data — actual reflective-journaling chat conversations — the fifth occurrence of this exact pattern in five consecutive epics (2, 3, 4, 5, now 6), and the first time the underlying structural cause (the dead `sl.reset()` trigger) has been pinned down directly. — **adversarial lens**
2. **The side drawer's "CONVERSAS" list surfaces the leaked state directly and is independently discoverable.** `AppDrawer`'s `_ConversasSection` reads `ChatReady.sessions` via `BlocBuilder<ChatCubit, ChatState>` — the same leaked state from finding 1. *Consequence*: a new user can see a list of a previous account's session titles/timestamps (titles can echo message content) before even opening a conversation, from the drawer alone. — **adversarial lens**
3. **`ChatSessionDto`/`ChatMessageDto` carry no user/account id, so the offline-cache fallback can't filter even if it tried — chat's own instance of the exact pattern Epic 3 found for entries.** The shared Hive boxes get dumped unfiltered on an offline-triggered fallback for whichever account is currently active. — **adversarial lens**
4. **The proactive-insight recency guard (`_insightRequestSeq`) is a single counter shared across every session, not scoped per session.** Triggering an insight on session A (slow to resolve), switching to session B and firing a second trigger there (bumping the shared counter), then switching back to A before request #1 resolves causes A's perfectly valid, non-superseded insight to be silently discarded — the guard's own comment claims it discards only a result superseded by "a later-fired request for the same window," but the counter has no session scoping to make that true. No test exercises this switch-away-then-back-with-an-intervening-other-session-trigger sequence. — **edge-case-hunter**
5. **No client-side timeout ceiling exists if the backend's RAG+LLM pipeline hangs after opening the SSE connection without ever emitting a byte — not even its own documented `AI_GENERATION_TIMEOUT` in-band event.** `receiveTimeout: Duration.zero` deliberately disables dio's own gap timeout, relying entirely on the backend's in-band event as the sole circuit breaker; `ChatCubit._consumeStream` has no `Future.timeout` of its own. *Consequence*: if the backend truly never sends anything, the AI bubble stays `streaming` and the composer stays locked for that session forever, with no client-side recovery short of switching sessions or restarting the app. — **edge-case-hunter**
6. **A message reloaded from history/cache with a persisted `streaming` status — a scenario this codebase's own comments explicitly anticipate — renders as a permanently blinking "zombie" bubble with no way out.** Only `failed`-status bubbles get a retry affordance; `retryMessage()`'s own guard silently no-ops against a `streaming`-status message. *Consequence*: a response abandoned in an earlier session (e.g. by finding 5's own hang, or any other dropped stream) reappears on reload as an indefinitely "typing" bubble the user can neither retry, dismiss, nor distinguish from a genuinely active stream. — **edge-case-hunter**
7. **`generateInsight()` collapses `'generating'`, `'failed'`, `'dismissed'`, and blank-but-non-null `'ready'` content all into the identical `Right(null)`.** `'generating'` is a valid, documented response status (per `openapi.yaml`) and is not a failure — the insight may still be computable server-side — but since no polling/GET endpoint exists for insights and the client's own trigger window has already reset by the time this resolves, a "still generating" result is permanently and silently lost, indistinguishable from a true failure or a genuinely empty result. — **edge-case-hunter**
8. **The proactive-insight message-count trigger fires on attempted sends, not completed ones — and this is exactly the risk `deferred-work.md`'s own spec-6-1 entry predicted, now confirmed materialized in 6.5.** That entry flagged `ChatCubit.sendMessage()`'s internal completer as never awaited by its caller, naming "a future story (6.5's insight-trigger counting is the named candidate)" as the exact risk. `_insightMessagesSinceWindowStart` increments unconditionally the moment `sendMessage()` is called, before the stream's outcome is known — a failed/dropped send counts identically to a successful one toward RF08's "N = 5 user messages" threshold. *Consequence*: a user whose messages keep failing (flaky connectivity that still briefly reports "online") can fire a proactive-insight generation grounded in a conversation that, server-side, may not actually contain those 5 messages. — **edge-case-hunter**; a predicted risk from Epic 6's own earlier story confirmed true by a later story in the same epic.
9. **A self-documented, currently-unresolved defect already exists in shipped code: an aborted connection mid-generation can show "failed" for an answer the backend actually generated successfully, and retry resends as a duplicate question instead of regenerating.** The code's own comment at `api_client.dart` explicitly documents that `receiveTimeout: Duration.zero`'s mitigation "does not fully work" — a connection can still abort mid-generation while the backend persists the answer; the aborted bubble then shows `failed`, and a retry (finding no `serverId`, since even `message_created` never arrived) resends via `sendMessage` as a brand-new message rather than regenerating in place. This is not a newly-discovered bug — it is already acknowledged in the code — but it remains open and user-facing, and connects to the already-known pattern (below) of local client state diverging from backend truth. — **adversarial lens**
