- (crack) Brainstorm's cache question (drift vs Hive, justified by RF06 AND-logic query complexity) rests on a false premise: source/dateFrom/dateTo filtering is 100% server-side query params on GET /entries and GET /entries/search (openapi.yaml). The client never runs that filter itself, online or cached.
- (lock) Entry domain model carries serverRevision (int) and updatedAt (timestamp), not sync_status. requirements.md section 8 data model table is wrong on this field per sync-badge.md; contract/backend docs win per requirements.md's own precedence rule. Sync badge (Synchronizing/Error/Synchronized) is derived client-side by comparing these two fields against pending local writes, never supplied by the server.
- (lock) Local cache: Hive, not drift. Two-ish boxes (entries by id, chat_messages by session id, chat_sessions by id) plus a pagination cursor string. No relational engine: nothing client-side ever filters, joins or sorts the cache -- every query dimension (source/dateFrom/dateTo, semantic search) is server-owned per openapi.yaml. Checked Priya's two counter-scenarios (local secondary sort on My Records, client-side dashboard fallback aggregation) against requirements.md -- neither is a stated requirement, both would be scope creep. Hive wins on evidence, not just simplicity preference.
- (kill) Vault: rejected biometric_storage package as the 'fewer deps' alternative the brainstorm floated. It gates storage access behind biometric success, which cannot satisfy RF03's explicit requirement that a biometric failure falls back to PIN without lockout -- checking the PIN would need the PIN hash, which would need biometric success to unlock, which is what just failed. Circular. Keep flutter_secure_storage (plain, non-biometric-gated item) for the PIN hash + local_auth for Face ID/Touch ID, both owned by one vault state machine.
- (lock) DI: plain get_it, no injectable/codegen. Each feature registers its own deps in a per-feature registration function called from main at startup.
- (lock) DTOs/domain entities: freezed + json_serializable, justified concretely -- Entry alone has 11 required fields per the openapi.yaml schema (id, content, source, chatMessageId, occurredAt, tags, piiStatus, piiSpans, embeddingStatus, mediaDurationSeconds, serverRevision, createdAt, updatedAt), hand-written == / copyWith for that is a bug magnet. Also used for sealed unions (Failure, Resource). Not blanket codegen on every class.
- (lock) Routing: go_router, single redirect callback keyed off one SessionStatus stream. No screen independently checks auth state or opts out of the gate.
- (lock) HTTP client: dio + exactly one interceptor owning apikey/Authorization headers per AGENTS.md's header rule. Retry logic fires only for server retryable:true codes (NETWORK_TIMEOUT, NETWORK_OFFLINE, PII_CHECK_FAILED, EMBEDDING_FAILED, AI_GENERATION_TIMEOUT, RATE_LIMITED) -- never for the 7 retryable:false codes (AUTH_EXPIRED, AUTH_INVALID, VALIDATION_ERROR, NOT_FOUND, EXPORT_EMPTY_PERIOD, PAYLOAD_TOO_LARGE, OCR_NO_TEXT).
- (lock) Failure hierarchy: sealed class with exactly 13 server-mirrored subtypes (full closed list from error-taxonomy.md: AuthExpired, AuthInvalid, NetworkTimeout, NetworkOffline, Validation, PiiCheckFailed, EmbeddingFailed, AiGenerationTimeout, NotFound, RateLimited, ExportEmptyPeriod, PayloadTooLarge, OcrNoText) plus exactly 1 local-only variant, MalformedResponse (retryable hardcoded false), for the 'malformed response' leg of RNF09's 3-failure-type test matrix -- that leg is NOT one of the 13 server codes, it is the client detecting a response that does not parse to the expected DTO shape. requirements.md section 11 lists only 10 of the 13 as 'minimum codes' -- the hierarchy must cover all 13, not just the 10 shown there.
- (decision) RNF09 test harness: mocktail-stubs a single ApiClient interface (thin dio wrapper) per repository test, not a fake network transport/adapter layer. One shared table-driven test helper drives the 5-write-endpoints x 3-failure-types = 15 scenario matrix so later units fill a table instead of writing 15 tests from scratch.
- (kill) Downgraded the brainstorm's 'one generic view-state enum shared by all nine screens' claim -- too strong. RF02's capture pipeline (recording/processing/transcribed/transcription-error) is its own state machine, not a data-fetch resource. RF07 depends on three independent streams at once (auth, sync badge, entry data) per its own acceptance criteria, not one Resource. Forcing either into a generic loading/error/data shape would be the wrong abstraction.
- (lock) Shared view-state: a generic Resource<T> (idle/loading/data/error) in core, used only by single-source-of-truth fetch screens (e.g. RF06 results list, RF09 dashboard). RF02's capture state machine and RF07's composite auth x sync x data state get their own feature-specific state classes -- not forced into Resource<T>.
- (decision) isolatedSideEffect helper (shared by RF08 and RF10's identical failure-isolation wording): the contract is decided now -- a never-throws wrapper returning Either<Failure,T> for an action that must not block its caller on failure -- but the implementation is deferred to RF10, its first real consumer in delivery order (RF04 -> RF10 -> RF08), not built speculatively in F000. It must live in core/ so RF08 can reuse it without a cross-feature import.
- (lock) Chart package: fl_chart, unchanged from the brainstorm -- pure Dart, no native bridge, matches the 3 fixed RF09 scenarios (0/1/>30 entries).
- (lock) Entry domain model carries serverRevision (int) and updatedAt (timestamp) fields, not sync_status -- requirements.md section 8's data model table is wrong on this field; sync-badge.md and the Entry schema in openapi.yaml both confirm no such column exists. The 3-state sync badge (Synchronizing/Error/Synchronized) is a pure function computed client-side from serverRevision/updatedAt plus pending local-write state, never supplied by the server.
- (note) AUTH_INVALID's description ('invalid credentials / biometrics') in requirements.md section 11 is imprecise: per the backend README, no biometric call ever reaches the server, so AUTH_INVALID can only ever originate from POST /auth/login (email+password). The vault's biometric/PIN gate stays 100% local with zero Either/Failure plumbing, consistent with the brainstorm's existing bedrock fact on this.
