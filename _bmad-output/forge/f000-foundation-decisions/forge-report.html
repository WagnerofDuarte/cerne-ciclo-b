BMad Forge Idea — Session Report

F000 Foundation Decisions

Cerne · reflective-journaling app · forged 2026-10-25

Outcome

The brainstorm's open branches for the F000 foundation unit — local cache, vault packaging, DI, DTO codegen, the Failure hierarchy, and the shared view-state/isolation abstractions — were driven to concrete decisions by checking each claim against requirements.md, openapi.yaml, and the rest of docs/input/backend/ rather than taken on the brainstorm's word. Two of the brainstorm's own claims didn't survive contact with the contract and were corrected rather than kept. The full record is in forged-idea.md next to this report.

Cast who pressure-tested this

🏗️ Winston — System Architect
Measured, trade-off-first. Drove the cache, DI, routing and HTTP-client calls, always tying the pick to what the contract actually demands rather than what's trendy.
🧭 Priya — RF06 implementer (generated voice)
The outside consequence-bearer: builds RF06 three units after F000 ships and has to live with whatever cache schema gets picked. Pushed the two concrete counter-scenarios that the Hive decision had to survive.

Locked decisions

  • lock Local cache: Hive, not drift — every filter/search dimension is a server-side query param; the client never filters, joins or sorts cached data.
  • lock Vault: flutter_secure_storage (plain PIN-hash item) + local_auth, one state machine.
  • lock DI: plain get_it, no codegen.
  • lock DTOs/entities: freezed + json_serializable, justified by Entry's 11 required fields.
  • lock Routing: go_router, single redirect off one SessionStatus stream.
  • lock HTTP client: dio + one header/retry interceptor, retries gated strictly on server retryable:true.
  • lock Chart: fl_chart.
  • lock Failure hierarchy: 13 server-mirrored subtypes + exactly 1 local-only MalformedResponse variant.
  • lock View-state: generic Resource<T> for simple fetch screens only — not RF02's capture pipeline, not RF07's composite state.
  • lock Entry model: serverRevision + updatedAt, no sync_status field.

Rejected / corrected

  • kill biometric_storage package as the "fewer deps" vault alternative — gating storage behind biometric success can't satisfy RF03's PIN-fallback requirement (circular: the PIN check would need biometric success to unlock the thing that's supposed to replace biometric success).
  • kill "One generic view-state enum for all nine screens" — downgraded. RF02's capture pipeline and RF07's three-stream composite state don't fit a loading/data/error shape; forcing them in would be the wrong abstraction.
  • corrected requirements.md §8 lists a sync_status column that doesn't exist — sync-badge.md and the Entry schema both confirm it's derived client-side from serverRevision/updatedAt.
  • corrected requirements.md §11's error table is a 10-of-13 excerpt — the Failure hierarchy is built from the full closed list in error-taxonomy.md.
  • corrected AUTH_INVALID's "credentials / biometrics" wording is imprecise — no biometric call ever reaches the server, so it can only originate from POST /auth/login.

Weak points that survived

isolatedSideEffect helper — the contract (never-throws wrapper, Either<Failure,T>) is decided, but its concrete shape is deliberately not built until RF10. If RF10's actual needs diverge from this guess, the helper may need reshaping when RF08 goes to reuse it.
RNF09 test harness — committed to mocktail-stubbing an ApiClient interface rather than a fake transport layer. This is lighter-weight but means the test suite never exercises real dio-level behavior (timeouts, interceptor ordering) directly — a deliberate trade, not a proven-safe one.
Dashboard cache-invalidation (RF09's acceptance criterion) was explicitly pushed out of F000's scope as a presentation-layer concern — correct by the "don't build speculatively" rule, but it means whoever builds RF09 inherits an undecided question with no F000 scaffolding to lean on.
